# 问题日志

只记录本项目运行中**真实发生**的问题（有日志、报错或运行 ID 为证）。预判的问题写在讲解文档里，不写在这里。

---

## P1：两个官方数据源的题目不一致

- 日期：2026-10-22
- 现象：HF 版和完整包版都是 500 题，但按 `question_id` 对比，HF 版有 119、120 两题在包里找不到，包里却没有 HF 找不到的题。
- 怎么发现的：`scripts/data_stats.py` 逐题对比两个版本的字段。
- 排查过程：两边题数相同但 ID 对不上，推断包内有重复 ID；统计后确认完整包（2024-06）中 137、138 各出现两次。HF 版把重复题换成了 119、120，并修正了 879、1322 两题的标准 SQL（例如 879 补上 `CAST(fastestLapSpeed AS REAL)`，原写法按字符串排序速度）。
- 根因：官方完整包里的题目文件是旧版，HF 是后来修正过的版本。
- 解决：题目和标准 SQL 只用 HF 版，完整包只取数据库文件（`scripts/download_data.py`）。见 ADR 001。
- 效果：用旧版会有 2 题重复计分、2 题按旧标准 SQL 判分，结果和公开数字不可比。

## P2：评测器超时口径与官方不一致，标准答案对比自身也会判错

- 日期：2026-10-22
- 现象：用官方判分函数跑"标准 SQL 对比自身"，只有 99.6%，518、701 判错；我们自己的评测器 518 判对。
- 怎么发现的：`scripts/official_crosscheck.py` 调用官方 `execute_model` 逐题判分，再和我们的结果逐题对照。
- 排查过程：
  1. 单独执行 701 的标准 SQL，耗时 157.9 秒，远超 30 秒，所以任何预测都判错；
  2. 518 单独执行约 29 秒，没超过 30 秒，官方却判错；
  3. 回到官方代码：`func_timeout(30, execute_sql, ...)` 包住的是"先执行预测、再执行标准"整个过程，两者共用 30 秒；而我们的实现给两条 SQL 各 30 秒。
- 根因：评测器的超时预算口径和官方不一致。
- 解决：`src/datapilot/ex.py` 改为先执行预测 SQL，标准 SQL 只用剩余时间；测试先行，补了 `test_pred_and_gold_share_one_time_budget` 等 2 个测试。
- 效果：修复后三组自检（对自身 / 打乱顺序 / SELECT 1）共 1500 次判分与官方逐题一致，不一致 0 处（gold-check-20261022-143358）。同时得出 EX 理论上限 99.6%。

## P3：标准 SQL 用了不带 ORDER BY 的 LIMIT，结果依赖执行计划

- 日期：2026-10-22
- 现象：自检"把标准 SQL 包一层子查询、打乱行顺序"应 100% 判对，实际 1144、751、349 三题稳定判错（重复 3 次都错）。
- 怎么发现的：评测自检（gold-check-20261022-142358）。
- 排查过程：单独执行这三题的标准 SQL，连续两次结果相同，排除随机性；再看 SQL，三题都用 `LIMIT` 取部分行但没有 `ORDER BY`（例如 751：`... WHERE T4.gender = 'Male' LIMIT 5`）。外面包一层子查询后执行计划变化，取到的是另外几行。
- 根因：标准答案本身不确定，返回哪几行取决于 SQLite 的执行计划。
- 解决：评测口径不改（改了就和官方不可比）；在 `docs/numbers.md` 标注，失败分析时这三题优先判为"标准答案问题"候选。
- 效果：说明 EX 会把语义等价的 SQL 判错，是 EX 指标缺陷的具体例子。

## P4：提示缓存从未命中

- 日期：2026-10-22
- 现象：试跑 60 次调用，`cache_read_input_tokens` 全部为 0。
- 怎么发现的：试跑后逐条看 usage（trial-20261022-144501-d822）。
- 排查过程：系统提示只有一句话，远低于可缓存的最小长度；占输入大头的 schema（300–2100 token）放在 user 消息里，`cache_control` 只打在 system 上，所以没有可复用的前缀。
- 根因：缓存断点位置不对，可复用的内容（同一数据库的 schema）没有放进被缓存的前缀。
- 解决：`src/datapilot/pipeline.py` 把 schema 放进 system（带 `cache_control`），问题和 evidence 放 user。因为改了提示词结构，单独跑一次"只移动 schema"的 E1，确认准确率不变。
- 效果（Sonnet 500 题）：缓存读取占输入 token 89%；花费 $2.69 → $1.32（-51%）；EX 71.8% → 70.8%，McNemar p=0.50，无显著变化（baseline-20261022-144835-8314 → e1-20261022-161608-d69f）。

## P5：离线门禁测不出评测器的顺序 bug

- 日期：2026-10-22
- 现象：故意把 `ex_match` 改坏成"按行顺序比较"，离线门禁（标准答案跑冒烟 20 题）仍然 100% 通过。
- 怎么发现的：写完门禁后做"故意改坏"验证（变异测试的思路），确认门禁真的能拦住错误。
- 排查过程：门禁让标准答案对比自身，两边执行的是同一条 SQL，行顺序天然一致，所以顺序类 bug 永远不会暴露；同理"只比行数"之类的 bug 也测不出来。
- 根因：检查用例和被检查对象相同，没有区分度。
- 解决：`evals/gate.py` 的离线检查改为三组：标准对标准必须全对；打乱行顺序必须全对；`SELECT 1` 命中的题必须与 gold-check 记录逐题一致。
- 效果：改坏为"按顺序比较"时 8 项失败，改坏为"只比行数"时 11 项失败；正常代码通过。

## P6：只读连接拦不住 ATTACH / PRAGMA / CREATE TEMP TABLE

- 日期：2026-10-22
- 现象：绕过 sqlglot 静态检查（`skip_guard=True`）后，`ATTACH DATABASE ':memory:'`、`PRAGMA journal_mode = DELETE`、`CREATE TEMP TABLE x (a)` 在 `mode=ro` 连接上都执行成功。
- 怎么发现的：代码审查指出 sqlglot 的 TokenError 未被捕获；修复时想让"sqlglot 解析不了的 SQL"交给 SQLite 执行，于是先补测试验证第二层防御是否可靠，测试失败。
- 排查过程：`mode=ro` 只保证不写主库文件；临时表写在 temp 库，ATTACH 和 PRAGMA 是连接级操作，都不受它限制。之前文档里写的"只读连接兜底"并不完整。
- 根因：把"库文件只读"误当成"连接只能读"。
- 解决：`src/datapilot/sql_guard.py` 加 `set_authorizer`，只放行 SELECT / READ / FUNCTION / RECURSIVE 和几个只读元数据 PRAGMA；sqlglot 解析失败不再直接拒绝，交给 SQLite 执行（与官方口径一致，写错的 SQL 能拿到 SQLite 原生报错去纠错）。同时修复 TokenError 未捕获导致整个评测可能中途崩溃的问题。
- 效果：4 类非读操作在无静态检查时全部被拦截（测试 `test_authorizer_blocks_non_read_ops_even_without_guard`）；500 道标准 SQL 复验与官方 1500 次判分 0 处不一致（gold-check-20261022-145326），没有误拦合法查询。

## P7：Opus 基线疑似数据污染（复现标准答案原文）

- 日期：2026-10-22
- 现象：全量基线 Opus 86.6%，比 Sonnet 高 15 个百分点；500 条预测里 241 条与标准 SQL 归一化后逐字相同（Sonnet 43、Haiku 29）。
- 怎么发现的：试跑时注意到 13/60 条与标准答案逐字相同；全量后按模型统计逐字复现率（baseline-20261022-144835-8314）。
- 排查过程：
  1. 逐字相同也可能是简单题写法唯一。但 Sonnet、Haiku 的复现率低得多，说明不是题目本身导致；
  2. 看风格痕迹：标准答案常用 `T1/T2` 别名，408 题里 Opus 也用 T1 的有 364 题（89%），Sonnet 56、Haiku 86；
  3. 分组：在 Opus 未逐字复现的 259 题上，Opus 74.1%、Sonnet 61.0%、Haiku 53.7%，差距缩小但仍在。
- 根因（推断，不能证明）：BIRD 2023 年公开，标准答案很可能进入了 Opus 的训练数据。
- 解决：报告中把 Opus 数字标注为"可能受污染"；D2 改进实验的主模型选择需本人拍板（见检查点 1）。
- 效果：避免把"背答案"的分数当成能力，也避免用 Opus 衡量改进（已接近上限，改进空间被污染掩盖）。

## P8：Sonnet 偶发生成失控，耗尽 16000 输出 token

- 日期：2026-10-22
- 现象：Sonnet E4 有 3 题 `no_sql`，`stop_reason=max_tokens`，每题输出 16000 token、只花一次调用就耗尽；单题 $0.16，占该次运行 Sonnet 总花费的 28%。
- 怎么发现的：看 E4 的非 ok 状态（e4-20261022-163051-724f），再统计全部运行。
- 排查过程：
  1. 用 4000 上限重跑同一题（q263），130 token 正常结束——不是题目本身的问题，是偶发；
  2. 统计全部运行：正常调用 3094 次，单次输出最大 885 token；失控 7 次，全部是 Sonnet（Haiku、Opus 为 0）；累计浪费约 $1.1；
  3. 修复时发现第二个坑：SDK 的 `messages.parse` 遇到截断的 JSON 会直接抛校验异常，拿不到 usage，这次调用的花费记不上账。
- 根因：模型偶发退化生成 + `max_tokens` 设得远高于实际需要（16000 vs 正常最大 885），每次失控都按满额计费。
- 解决：`src/datapilot/llm.py` 把 `max_tokens` 降到 4096，撞到上限自动重试一次，usage 按两次累计；结构化输出改为 `create` + 自己解析，解析失败时 usage 仍可记账。
- 效果：单次失控代价从 $0.16 降到约 $0.045，且大概率能救回答案（复现时重跑一次即正常）。效果数字待下一次 Sonnet 全量运行确认。

## P9：Schema 检索让提示缓存失效，花费超预估 70%

- 日期：2026-10-22
- 现象：检索消融预估约 $1.8，实际跑到 373 题就撞上 $3 硬上限；单题成本 $0.0082，是 E4 的 2.9 倍。
- 怎么发现的：runner 的 `--max-cost` 触发停止（abl-20261022-164533-638f）。
- 排查过程：对比 usage，E4 的输入大部分是缓存读取（0.1 倍价），检索版几乎全是缓存写入（1.25 倍价）。原因是检索后每道题的 schema 子集不同，system 前缀各不相同，缓存无法复用。预估公式只按"未缓存输入"估算，没有考虑"缓存写入比原价更贵"。
- 根因：个性化的提示词前缀和提示缓存天然冲突。
- 解决：不采用检索（同时准确率显著下降 p=0.013）；结论写入 ADR 002 结果。硬上限保证了超支可控。
- 效果：避免了在一个更差、更贵的方案上继续花钱；也说明缓存设计要和提示词结构一起考虑。

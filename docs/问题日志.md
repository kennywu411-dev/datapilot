# 问题日志

只记录本项目运行中真实发生的问题（有日志、报错或运行 ID 为证）。预判的问题写在讲解文档里，不写在这里。

---

## P1：两个官方数据源的题目不一致

- 现象：HF 版和完整包版都是 500 题，但按 `question_id` 对比，HF 版有 119、120 两题在包里找不到，包里却没有 HF 找不到的题。
- 怎么发现的：`scripts/data_stats.py` 逐题对比两个版本的字段。
- 排查过程：两边题数相同但 ID 对不上，推断包内有重复 ID；统计后确认完整包（2024-06）中 137、138 各出现两次。HF 版把重复题换成了 119、120，并修正了 879、1322 两题的标准 SQL（例如 879 补上 `CAST(fastestLapSpeed AS REAL)`，原写法按字符串排序速度）。
- 根因：官方完整包里的题目文件是旧版，HF 是后来修正过的版本。
- 解决：题目和标准 SQL 只用 HF 版，完整包只取数据库文件（`scripts/download_data.py`）。见 ADR 001。
- 效果：用旧版会有 2 题重复计分、2 题按旧标准 SQL 判分，结果和公开数字不可比。

## P2：评测器超时口径与官方不一致，标准答案对比自身也会判错

- 现象：用官方判分函数跑"标准 SQL 对比自身"，只有 99.6%，518、701 判错；我们自己的评测器 518 判对。
- 怎么发现的：`scripts/official_crosscheck.py` 调用官方 `execute_model` 逐题判分，再和我们的结果逐题对照。
- 排查过程：
  1. 单独执行 701 的标准 SQL，耗时 157.9 秒，远超 30 秒，所以任何预测都判错；
  2. 518 单独执行约 29 秒，没超过 30 秒，官方却判错；
  3. 回到官方代码：`func_timeout(30, execute_sql, ...)` 包住的是"先执行预测、再执行标准"整个过程，两者共用 30 秒；而我们的实现给两条 SQL 各 30 秒。
- 根因：评测器的超时预算口径和官方不一致。
- 解决：`src/datapilot/ex.py` 改为先执行预测 SQL，标准 SQL 只用剩余时间；测试先行，补了 `test_pred_and_gold_share_one_time_budget` 等 2 个测试。
- 效果：修复后三组自检（对自身 / 打乱顺序 / SELECT 1）共 1500 次判分与官方逐题一致，不一致 0 处（gold-check-d1190b）。同时得出 EX 理论上限 99.6%。

## P3：标准 SQL 用了不带 ORDER BY 的 LIMIT，结果依赖执行计划

- 现象：自检"把标准 SQL 包一层子查询、打乱行顺序"应 100% 判对，实际 1144、751、349 三题稳定判错（重复 3 次都错）。
- 怎么发现的：评测自检（gold-check-826eb7）。
- 排查过程：单独执行这三题的标准 SQL，连续两次结果相同，排除随机性；再看 SQL，三题都用 `LIMIT` 取部分行但没有 `ORDER BY`（例如 751：`... WHERE T4.gender = 'Male' LIMIT 5`）。外面包一层子查询后执行计划变化，取到的是另外几行。
- 根因：标准答案本身不确定，返回哪几行取决于 SQLite 的执行计划。
- 解决：评测口径不改（改了就和官方不可比）；在 `docs/numbers.md` 标注，失败分析时这三题优先判为"标准答案问题"候选。
- 效果：说明 EX 会把语义等价的 SQL 判错，是 EX 指标缺陷的具体例子。

## P4：提示缓存从未命中

- 现象：试跑 60 次调用，`cache_read_input_tokens` 全部为 0。
- 怎么发现的：试跑后逐条看 usage（trial-c0b9f9）。
- 排查过程：系统提示只有一句话，远低于可缓存的最小长度；占输入大头的 schema（300–2100 token）放在 user 消息里，`cache_control` 只打在 system 上，所以没有可复用的前缀。
- 根因：缓存断点位置不对，可复用的内容（同一数据库的 schema）没有放进被缓存的前缀。
- 解决：`src/datapilot/pipeline.py` 把 schema 放进 system（带 `cache_control`），问题和 evidence 放 user。因为改了提示词结构，单独跑一次"只移动 schema"的 E1，确认准确率不变。
- 效果（Sonnet 500 题）：缓存读取占输入 token 89%；花费 $2.69 → $1.32（-51%）；EX 71.8% → 70.8%，McNemar p=0.50，无显著变化（baseline-93aca7 → e1-aed243）。

## P5：离线门禁测不出评测器的顺序 bug

- 现象：故意把 `ex_match` 改坏成"按行顺序比较"，离线门禁（标准答案跑冒烟 20 题）仍然 100% 通过。
- 怎么发现的：写完门禁后做"故意改坏"验证（变异测试的思路），确认门禁真的能拦住错误。
- 排查过程：门禁让标准答案对比自身，两边执行的是同一条 SQL，行顺序天然一致，所以顺序类 bug 永远不会暴露；同理"只比行数"之类的 bug 也测不出来。
- 根因：检查用例和被检查对象相同，没有区分度。
- 解决：`evals/gate.py` 的离线检查改为三组：标准对标准必须全对；打乱行顺序必须全对；`SELECT 1` 命中的题必须与 gold-check 记录逐题一致。
- 效果：改坏为"按顺序比较"时 8 项失败，改坏为"只比行数"时 11 项失败；正常代码通过。

## P6：只读连接拦不住 ATTACH / PRAGMA / CREATE TEMP TABLE

- 现象：绕过 sqlglot 静态检查（`skip_guard=True`）后，`ATTACH DATABASE ':memory:'`、`PRAGMA journal_mode = DELETE`、`CREATE TEMP TABLE x (a)` 在 `mode=ro` 连接上都执行成功。
- 怎么发现的：代码审查指出 sqlglot 的 TokenError 未被捕获；修复时想让"sqlglot 解析不了的 SQL"交给 SQLite 执行，于是先补测试验证第二层防御是否可靠，测试失败。
- 排查过程：`mode=ro` 只保证不写主库文件；临时表写在 temp 库，ATTACH 和 PRAGMA 是连接级操作，都不受它限制。之前文档里写的"只读连接兜底"并不完整。
- 根因：把"库文件只读"误当成"连接只能读"。
- 解决：`src/datapilot/sql_guard.py` 加 `set_authorizer`，只放行 SELECT / READ / FUNCTION / RECURSIVE 和几个只读元数据 PRAGMA；sqlglot 解析失败不再直接拒绝，交给 SQLite 执行（与官方口径一致，写错的 SQL 能拿到 SQLite 原生报错去纠错）。同时修复 TokenError 未捕获导致整个评测可能中途崩溃的问题。
- 效果：4 类非读操作在无静态检查时全部被拦截（测试 `test_authorizer_blocks_non_read_ops_even_without_guard`）；500 道标准 SQL 复验与官方 1500 次判分 0 处不一致（gold-check-d63784），没有误拦合法查询。

## P7：Opus 基线疑似数据污染（复现标准答案原文）

- 现象：全量基线 Opus 86.6%，比 Sonnet 高 15 个百分点；500 条预测里 241 条与标准 SQL 归一化后逐字相同（Sonnet 43、Haiku 29）。
- 怎么发现的：试跑时注意到 13/60 条与标准答案逐字相同；全量后按模型统计逐字复现率（baseline-93aca7）。
- 排查过程：
  1. 逐字相同也可能是简单题写法唯一。但 Sonnet、Haiku 的复现率低得多，说明不是题目本身导致；
  2. 看风格痕迹：标准答案常用 `T1/T2` 别名，408 题里 Opus 也用 T1 的有 364 题（89%），Sonnet 56、Haiku 86；
  3. 分组：在 Opus 未逐字复现的 259 题上，Opus 74.1%、Sonnet 61.0%、Haiku 53.7%，差距缩小但仍在。
- 根因（推断，不能证明）：BIRD 2023 年公开，标准答案很可能进入了 Opus 的训练数据。
- 解决：报告中把 Opus 数字标注为"可能受污染"。
- 效果：避免把"背答案"的分数当成能力，也避免用 Opus 衡量改进（已接近上限，改进空间被污染掩盖）。

## P8：Sonnet 偶发生成失控，耗尽 16000 输出 token

- 现象：Sonnet E4 有 3 题 `no_sql`，`stop_reason=max_tokens`，每题输出 16000 token、只花一次调用就耗尽；单题 $0.16，占该次运行 Sonnet 总花费的 28%。
- 怎么发现的：看 E4 的非 ok 状态（e4-3463b8），再统计全部运行。
- 排查过程：
  1. 用 4000 上限重跑同一题（q263），130 token 正常结束，不是题目本身的问题，是偶发；
  2. 统计全部运行：正常调用 3094 次，单次输出最大 885 token；失控 7 次，全部是 Sonnet（Haiku、Opus 为 0）；累计浪费约 $1.1；
  3. 修复时发现第二个坑：SDK 的 `messages.parse` 遇到截断的 JSON 会直接抛校验异常，拿不到 usage，这次调用的花费记不上账。
- 根因：模型偶发退化生成 + `max_tokens` 设得远高于实际需要（16000 vs 正常最大 885），每次失控都按满额计费。
- 解决：`src/datapilot/llm.py` 把 `max_tokens` 降到 4096，撞到上限自动重试一次，usage 按两次累计；结构化输出改为 `create` + 自己解析，解析失败时 usage 仍可记账。
- 效果（e4rep-7206c1，Sonnet 两轮 1000 次）：失控只剩 1 次，代价 $0.08（修复前 $0.16）；Sonnet 单轮花费 $1.74 → $1.33。判断修正：剩下那次仍是 q263，重试也失控，不完全是随机的，个别题本身容易诱发失控，重试救不回来；上限仍然限住了损失。

## P9：Schema 检索让提示缓存失效，花费超预估 70%

- 现象：检索消融预估约 $1.8，实际跑到 373 题就撞上 $3 硬上限；单题成本 $0.0082，是 E4 的 2.9 倍。
- 怎么发现的：runner 的 `--max-cost` 触发停止（abl-99761b）。
- 排查过程：对比 usage，E4 的输入大部分是缓存读取（0.1 倍价），检索版几乎全是缓存写入（1.25 倍价）。原因是检索后每道题的 schema 子集不同，system 前缀各不相同，缓存无法复用。预估公式只按"未缓存输入"估算，没有考虑"缓存写入比原价更贵"。
- 根因：个性化的提示词前缀和提示缓存天然冲突。
- 解决：不采用检索（同时准确率显著下降 p=0.013）；结论写入 ADR 002 结果。硬上限保证了超支可控。
- 效果：避免了在一个更差、更贵的方案上继续花钱；也说明缓存设计要和提示词结构一起考虑。

## P10：缓存 key 的规范化把引号里的取值也转成了小写

- 现象：构造缓存压测请求时，一条改写样例是 `WHEN DID 'CHL' CAST ITS FIRST VOTE...`，按当时的规范化（整句转小写）会和 `'chl'` 命中同一条缓存。
- 怎么发现的：跑压测前打印构造出的请求样例，逐条看（cache_bench 构造阶段）。
- 排查过程：规范化是为了让"前 5 名？"和"前 5 名"、"Top5"和"top5"命中同一条缓存；但引号里通常是数据库里的取值，SQLite 的 `=` 区分大小写，`gender = 'F'` 和 `gender = 'f'` 查出来的结果可能完全不同。整句转小写会让两个不同的问题共用一个答案。
- 根因：规范化的粒度太粗，没有区分"措辞"和"取值"。
- 解决：`src/datapilot/service.py` 的 `normalize_question` 只把引号外的文字转小写，引号内原样保留；补测试 `test_normalize_keeps_case_inside_quotes`。
- 效果：`'F'` 与 `'f'` 不再共用缓存；措辞上的大小写、标点、空白差异仍能命中。

## P11：回答只看前 20 行，把完整结果误判为"数据不全"

- 现象：问"每个赛季有多少场比赛？按年份看趋势"，查询返回了全部 68 行，回答却说"只返回了前 20 行，1970 年以后的趋势无法判断"。
- 怎么发现的：在前端逐轮试用时读回答文字。
- 排查过程：SQL 和表格都对，问题在生成回答那一步，为了省 token，只把前 20 行交给模型，提示里也没说一共多少行，模型自然以为数据只有 20 行。
- 根因：给模型的上下文被截断了，却没告诉它截断了。
- 解决：`src/datapilot/service.py` 回答阶段最多给 100 行，并在提示里写明"共 N 行，以下是全部结果 / 只展示前 K 行，不要只依据这部分下结论"；补测试 `test_answer_prompt_states_row_counts`；缓存配置版本升级使旧回答失效。
- 效果：68 行的结果完整交给模型；超过 100 行时模型会被明确告知只看到了一部分。

## P12：代码包在 macOS 命令行 unzip 下解压失败

- 现象：按 README 在干净目录复现时，`unzip` 解压代码包到 `docs/adr/001-数据来源与评测口径.md` 报 "write error (disk full?)" 并停下等待输入，命令挂住。
- 怎么发现的：生成代码包后，在临时目录里解压、照 README 从头复现（第 2.4 节"可复现"）。
- 排查过程：`df` 显示磁盘还剩 149GB，排除空间问题；同一个包用 `ditto`（访达解压同款）正常、中文文件名完好；`unzip -v` 显示是 2009 年的 UnZip 6.00，对 zip 里的 UTF-8 文件名处理有问题。
- 根因：zip 格式的文件名编码在不同解压工具间不统一，老版本 unzip 不认 UTF-8 标记。
- 解决：`scripts/package.sh` 改为 `git archive --format=tar.gz`，并在打包后自动解压到临时目录、检查中文文件名是否完好。
- 效果：tar 在 macOS / Linux / Windows 10+ 都自带，中文文件名正常。

## P13：.gitignore 的 data/ 误伤了 web/src/data，干净检出时前端构建失败

- 现象：代码包在干净目录里复现，`npm run build` 报 `Module not found: Can't resolve '@/data/eval.json'`；本机一直能跑。
- 怎么发现的：阶段 5 代码审查时注意到 `git ls-files` 里没有看板数据，随后干净目录复现的构建步骤失败，得到证实。
- 排查过程：`git check-ignore -v web/src/data/eval.json` 指向 `.gitignore:7: data/`，不带前导斜杠的规则会忽略任意层级的 data 目录。本机能跑是因为文件恰好在工作区里。修复时又踩了一个坑：在规则行尾写注释，`.gitignore` 不支持行尾注释，整行被当成规则，根目录 `data/` 反而不再被忽略。
- 根因：忽略规则写得太宽；"本机能跑"掩盖了"仓库里缺文件"。
- 解决：改为只匹配根目录的 `/data/`（注释单独一行）；打包脚本的兜底检查同步改为 `^data/`。
- 效果：`web/src/data/eval.json` 进入仓库；干净目录复现构建通过（见 阶段 5 复现记录）。

## P14：排队中的请求收不到任何事件，用户干等 10 秒

- 现象：v1.2 压测 50 并发未命中缓存时，成功请求的首个 SSE 事件 P50 是 10.55 秒；单个请求时只要 1.51 秒。
- 怎么发现的：压测脚本除了总延迟，还单独记了"首个事件延迟"。总延迟变长在预期之内（排队），首个事件也跟着变长才是问题。
- 排查过程：服务端先 `await` 信号量，拿到名额后才进入流程，第一个 step 事件要等生成 SQL 的那次模型调用结束才发出。排队期间流里只有空的连接，前端一直显示"理解问题…"，用户分不清是在排队、在算还是卡死了。
- 根因：并发保护只考虑了"保护下游"，没考虑等待中的用户需要反馈。
- 解决：名额已满时先发一个 `step` 事件 `queue`（"排队等待"），再去等名额；前端统计步骤数时不计这一步。补了两个测试：名额满时不用等就先收到排队事件；名额空闲时不发。
- 效果：首个事件 P50 在 16 并发从 4.51 秒降到 0.008 秒，50 并发从 10.55 秒降到 0.016 秒（`load-29bd23` → `load-8f1f7f`）；总延迟和吞吐不变。


## P15：百炼免费额度用完后被当成"单题失败"，qwen3.7-plus 全量作废

- 现象：qwen3.7-plus 500 题跑完显示 EX 50.0%，比 20 题试跑的 17/20 低得多；状态里 117 题 llm_error、34 题 no_sql。
- 怎么发现的：EX 和试跑差太多，按状态分组看报错原文（`ABORTED-qwen37-500-460ac1`）。
- 排查过程：
  1. llm_error 全是 HTTP 403，且从第 380 题左右开始连续出现，不是零星限流；
  2. 手动调一次接口，返回 `AllocationQuota.FreeTierOnly`：账户开着"仅使用免费额度"，额度用完后直接拒绝；
  3. runner 把所有异常都记成 llm_error 继续跑，账户层面的错误被当成了 117 道"单题失败"；
  4. 另外 34 题 no_sql 是模型返回了内容但没按 `{"sql": ...}` 解析成功（当时没记原话，无法确认具体格式）。
- 根因：两个，①没有区分"这一题失败"和"账户不能用了"；②解析只认严格 JSON。
- 解决：401 / 402 / 403 抛 `FatalAPIError`，评测立即停止并提示 `--resume`；`parse_loose` 去代码块、截取 `{...}`、字段名不区分大小写；no_sql 时把模型原话写进 detail（`src/datapilot/llm.py`、`evals/runner.py`）。
- 效果：该次运行标记 ABORTED 不计入结论；修复后重跑（运行 ID 见 numbers.md）。

## P16：DeepSeek 偶发输出失控（和 P8 的 Sonnet 同类）

- 现象：deepseek-flash 500 题里 5 题 no_sql，其中 4 题（q83、q189、q944、q1175）每次都把 4096 个输出 token 用满，重试一次仍然用满。
- 怎么发现的：看 no_sql 题的 stop_reason 和输出 token 数（`deepseek500-ae215c`）。
- 根因：模型偶发停不下来；P8 的"上限 4096 + 重试一次"防住了成本（每题最多 8192 token），但这 4 题仍然没有答案。另外 deepseek-flash 正常也每题输出约 1000 token（其他模型约 100），P95 延迟 28.5 秒。
- 解决：如实计为失败（最多影响 0.8 个百分点）；生产可加"失控即换模型"的路由（同 v1.3 智能路由思路）。

## P17：提示里附完整 JSON schema，qwen3.7-plus 把 schema 原样抄回来当答案

- 现象：修好 P15 后重跑 qwen3.7-plus，前 142 题里 26 题仍然 no_sql（约 18%）。
- 怎么发现的：P15 时加了"no_sql 记录模型原话"，这次直接看到原话：模型返回的是 `{"properties": {"sql": {...}}, "required": ["sql"], "title": "SQLAnswer", ...}`，正是提示里给它的 JSON schema。
- 排查过程：
  1. 上一次（P15）的 34 题 no_sql 当时没记原话，只能猜是格式问题，加了宽松解析，治标没治本；
  2. 这次有了原话，确认是模型把 schema 当成了"要输出的 JSON"；
  3. deepseek-flash 用同一提示 500 题只有 1 题（q576）疑似同类，说明不同模型对提示格式的敏感度差别很大。
- 根因：JSON 模式要求提示里出现 "json"，我图省事把完整 schema 附在 system 末尾；对字段只有一个的输出，schema 比示例更容易被误读。
- 解决：改为字段示例 `Reply with only one JSON object of the form {"sql": "..."}`（`src/datapilot/llm.py`），测试断言提示里不再出现 `properties`。
- 效果：之前失败的 28 题用新提示重跑，28/28 产出 SQL（`qwen37-fixcheck-*`）；第二次重跑标记 ABORTED，第三次全量见 numbers.md。
- 教训：P15 的修复是根据猜测做的；先把"现场"（模型原话）记下来，再修，才修到了根上。

## P19：行级权限静默过滤，让模型给出"看起来正确"的误导性答案

- 现象：权限评测消融（不把权限说明告诉模型）时，上海区域经理问"北京用户 2025 年一共下了多少单"，Haiku 和 Sonnet 都回答"0 单"。
- 怎么发现的：对比带 / 不带权限说明两轮的回答（`rls-eval-99d7a2`、`rls-nonote-606296`）。
- 根因：行过滤在执行层静默生效，SQL 和结果都"正常"，模型和用户都不知道结果被截了范围。列权限有明确的拒绝信号（报错 / 表结构标"无权访问"），行权限没有。
- 解决：保持代码强制不变，另把权限范围告诉模型（`Policy.prompt_note()`，系统提示和回答提示各一份），并要求回答说明"只包含有权限的范围"。
- 效果：说明范围的回答从 4/26 提到 26/26；需要无权限数据时如实告知从 8/16 提到 16/16；两轮越权都是 0。

## P20：行权限改写被同名 CTE 绕过（代码审查发现）

- 现象：上海区域经理执行 `WITH users AS (SELECT 'U0002' AS user_id, '上海' AS city) SELECT COUNT(*) FROM orders` 拿到了非上海用户的 8 单；执行 `SELECT (WITH orders AS (SELECT 1) SELECT 1), COUNT(*) FROM orders` 拿到全部 6000 单（应为 917）。
- 怎么发现的：合并前代码审查，逐条构造绕过 SQL 实测。43 个绕过测试没覆盖这两种写法。
- 根因：①行过滤条件里的表没写 schema（`FROM users`），插进用户查询后被用户自己定义的同名 CTE 遮蔽；②CTE 名字是全局收集的，没考虑作用域，子查询里的同名 CTE 让外层对真实表的引用被当成 CTE 跳过改写。授权回调只能按列拒绝，兜不住行。
- 解决：过滤条件里的表一律改写成 `main.表名`（CTE 遮不住限定名）；受限角色下禁止 CTE 与真实表同名（fail closed）；补 3 个回归测试。
- 效果：两种写法都被拒绝；40 道标准答案自检结果不变。

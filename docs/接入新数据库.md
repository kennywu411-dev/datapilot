# 接入新数据库并跑评测

目标：新库能在问数界面里用，并且有一组可复现的评测数字。每一步都有验收标准，不满足就先修好再往下。

## 0. 先确认三件事

1. 源库路径，以及给它起的 `db_id`（只能是字母、数字、下划线）。
2. 这个库是否允许复制到本项目的 `data/` 下（`data/` 不进 git，但会留在本机）。
3. 评测题从哪来。标准 SQL 必须由熟悉业务的人确认，否则评的只是出题人自己的理解。

## 1. 复制数据库并生成列说明草稿

```bash
uv run python scripts/add_database.py <db_id> <源库路径>
```

- 脚本只复制、不修改源库；目标已存在会拒绝覆盖。
- 它会从建表语句的行尾注释（如 `tier TEXT -- normal / vip`）提取取值说明，写到 `data/dev_databases/<db_id>/database_description/<表>.csv`。
- 验收：`uv run python -c "from datapilot import tools; print(tools.list_tables('<db_id>'))"` 能列出所有表。

## 2. 补全列说明（最值得花时间的一步）

打开每个 `database_description/<表>.csv`，补 `column_description`，重点补 `value_description`：
- 枚举列的全部取值和含义（`F: female; M: male`）；
- 日期格式（`YYYY-MM-DD` 还是 `YYMMDD`）；
- 单位（元 / 分、厘米 / 米）。

原因：DataPilot 的增强 schema 会把这些说明给模型看；本项目的失败分析里，取值写错和口径误解是可修的主要错误类型（见 `docs/问题日志.md` 和 `docs/failure/判定表.md`）。

## 3. 写评测题

在 `data/custom/<db_id>.json` 写题，格式与 BIRD 相同：

```json
[{"question_id": 1, "db_id": "<db_id>", "question": "VIP 用户有多少？",
  "evidence": "VIP 指 tier = 'vip'", "SQL": "SELECT COUNT(*) FROM users WHERE tier = 'vip'",
  "difficulty": "simple"}]
```

- 覆盖：计数、筛选、分组排序、多表关联、时间范围、占比，simple / moderate / challenging 都要有。
- 有业务口径的词（"活跃用户""退款率"）一定写进 `evidence`。
- 要有区分度：至少 1/3 的题不在 evidence 里给口径（如"活跃用户"不解释）、或需要多步推理（同比、排名后再筛选、多表关联后再聚合）。接入 opspilot 库时，15 道口径全给的题 Haiku 和 Sonnet 都是 100%（置信区间 80–100%），说明题出简单了，测不出差别。
- 避免 BIRD 踩过的坑：`LIMIT` 必须配 `ORDER BY`（否则结果依赖执行计划，P3）；问"多少人"就 `COUNT(DISTINCT ...)`；题目要几列就返回几列。

## 4. 校验标准答案（不花钱）

```bash
uv run python evals/runner.py --models gold --pipeline e4_correct --questions data/custom/<db_id>.json --tag selfcheck-<db_id>
```

- 验收：EX 必须是 100%。不是 100% 说明某条标准 SQL 报错、超时或被值核对拦下，逐条修好再继续。
- 再看一眼每条标准 SQL 的结果是否为空、是否全 NULL，空结果的题评测时区分不出对错。

## 5. 先看预算，再用真实模型评测

先不加 `--yes` 看预估：

```bash
uv run python evals/runner.py --models haiku,sonnet --pipeline e4_correct --questions data/custom/<db_id>.json --tag <db_id>
```

确认预算后再加 `--yes --max-cost <上限>` 运行。

## 6. 失败分析

对每道失败题，按 `docs/failure/判定表.md` 的标准分类（模型错 / 标准答案错 / 题目歧义 / 评测缺陷）并写明理由。自己写的标准答案也会错，BIRD 官方题的失败里有 56% 是标准答案的问题。

## 7. 登记与交付

- 数字写进 `docs/numbers.md`，注明运行 ID、题数、模型、花费；题数少于 50 时写上置信区间（`evals/report.py` 已输出）。
- 在问数界面（`http://localhost:3000`）左上角选新库，实际问 2–3 个问题，确认表结构和示例问题都能显示。
- 评测题和数据库文件都在 `data/` 下，不进 git，也不进代码包。

## 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 第 4 步不是 100% | 标准 SQL 报错、超时，或取值不存在被值核对拦下 | 看 `runs/selfcheck-<db_id>-*/results.jsonl` 的 status 和 detail |
| 模型总把枚举值写错 | 列说明没写取值 | 回第 2 步补 `value_description` |
| 表名是 SQL 关键字（如 `order`） | 模型照抄会语法错误 | 增强 schema 已自动加引号，无需处理 |
| 新库很大，查询慢 | 无索引的大表扫描 | 预跑标准 SQL 看耗时；超过 30 秒的题按官方口径必然判错 |

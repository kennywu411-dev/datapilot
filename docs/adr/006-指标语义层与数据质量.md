# ADR 006：指标语义层与数据质量（数据中台的指标层）

- 状态：已采纳

## 背景

口径消融（numbers.md）显示：模拟电商库 40 题去掉 evidence 后，所有模型从 93–98% 掉到 55–66%，换更贵的模型补不回来。原来的口径写在每道题的 evidence 里，这不是真实用法——用户提问时不会附带"有效订单指 status 不是 cancelled 和 pending"。口径应该由系统统一维护、提问时自动带上，并且和行列级权限兼容。

## 决定 1：指标字典用 YAML，按"公司口径"写，不按题写

`src/datapilot/metrics/shop_ops.yaml` 五部分：

| 部分 | 内容 | 例 |
|---|---|---|
| conventions | 全局约定，每次提问都带 | 订单类指标按下单时间归属；时间差用 julianday；金额分档左闭右开 |
| terms | 业务术语（过滤条件） | 有效订单 = `orders.status NOT IN ('cancelled', 'pending')` |
| metrics | 指标：口径、计算片段、过滤条件、主表、同义词 | 销售额 = `SUM(orders.amount)` + 有效订单 |
| dimensions | 维度：表达式、取值含义 | 品类 = `products.category`，月份 = `substr({time}, 1, 7)` |
| joins | 表关联，子表 → 父表 | `[orders, products, orders.sku = products.sku]` |

- 指标分两类：**simple**（一个聚合表达式 + 过滤条件，语义层能直接生成 SQL）和 **derived**（比率、同比、复购这类，只给口径和参考 SQL）。不为了"全都能生成"去设计一套表达式语言。
- 所有 SQL 片段里的列都写成"表名.列名"：加载时逐个校验列存在；同时据此算出血缘（指标依赖哪些表和列）和权限（依赖了哪些受限列）。
- 选 YAML 不选 TOML：中文说明和同义词列表多，YAML 可读性更好；pyyaml 已经是依赖链里的包。

## 决定 2：匹配用同义词最长匹配 + 字二元组模糊检索兜底，不用 BM25

- 精确匹配：所有指标和术语的名称、同义词按长度倒序做不重叠匹配，"有效订单数"不会再拆出"订单数"。
- 兜底：一个指标都没命中时，只在没被精确命中的文字上，按"同义词的字二元组有多少出现在问题里"打分，覆盖率 ≥ 0.6 取最高的一个。
- 不用 BM25：指标只有十几个、同义词很短，IDF 不稳定。试过以后，"一共有多少位超级会员"会因为"多少"命中"销量"（同义词"卖了多少件"）。
- 结果：原 40 题精确率 94.9%、召回率 92.5%；字典定稿后再写的 19 道留出题精确率 94.1%、召回率 84.2%（`evals/metric_match.py`，离线、不花钱）。

## 决定 3：默认"口径注入"，不用"语义层直出 SQL"

两种接法都做成包在 E4 外面的流程（和智能路由一样的包装方式），用实验决定：

| 方式 | 做法 |
|---|---|
| A 口径注入（`sem_context`） | 匹配到的指标、术语和全局约定并入 External Knowledge，模型照常写 SQL |
| B 语义层直出（`sem_compile`） | 先让模型把问题映射成"一个 simple 指标 + 维度 + 过滤 + 时间范围 + 排序"，由语义层拼 SQL；映射不了或执行出错退回 A |

去口径 40 题，Haiku / Sonnet 各 3 次（运行 ID 见 numbers.md）：

| | 无语义层 | A 口径注入 | B 语义层直出 |
|---|---|---|---|
| Haiku | 65.8% | **92.5%** | 87.5% |
| Sonnet | 64.2% | **95.0%** | 90.0% |

- A 相对无语义层每次运行都显著（p ≤ 0.002），且没有一题"有语义层反而答错"。
- B 比 A 平均低 2 题：41% 的题被直出，直出的题里有两类稳定出错——"来自成都的女性用户有多少人"被硬套成"购买用户数"指标（加了有效订单条件）；"2025 年双 11 大促"被映射成 11 月 11 日这一天的时间范围，而不是活动过滤。映射一错就没有纠错机会，A 则让模型在完整 schema 上自己判断。
- 所以问数服务默认 A。B 保留为可选流程：它的价值在于 SQL 可审计、和指标定义逐字一致，适合报表类固定查询，不适合开放问答。

## 决定 4：只沿多对一方向补 JOIN

语义层直出时从主表出发补 JOIN，只沿 [子表, 父表] 方向走。反方向是一对多，会把每行复制（扇出）：按品类数注册用户会变成数订单。这个问题是写目录页"可分析维度"的测试时发现的（问题日志 P22）。

## 决定 5：和行列级权限兼容

- 口径注入：指标依赖当前角色看不到的列（毛利依赖 `products.cost`）时，不给计算片段，只告诉模型"无权访问，不能计算"。
- 语义层直出：同样情况直接返回 `NO_PERMISSION`。
- 不管哪种方式，最终 SQL 照常经过 rls 改写和授权回调；语义层不是一条新的执行路径。测试覆盖：受限角色编译毛利被拒、区域经理按城市分组只看到上海、把指标表达式直接拼进 SQL 也被授权回调拒绝。
- 指标目录对所有角色可见（列名在表结构里本来就可见），受限列标在 `restricted` 里。

## 决定 6：数据质量检查规则化，报告只给主键

`src/datapilot/quality.py` + `quality_rules/shop_ops.yaml`：

| 类别 | 来源 | 例 |
|---|---|---|
| 主键为空 / 重复、外键一致性 | 按库里声明的约束自动生成 | `tickets.order_id` 都能在 `orders` 找到 |
| 业务键重复 | 规则 | 同一用户同一时刻同一商品两笔订单（疑似重复导入） |
| 空值、枚举、数值范围 | 规则 | `orders.status` 只取 6 个值；`campaigns.discount_rate` 在 0–1 |
| 行级业务规则 | 规则（SQL 条件） | 已签收订单必须有签收时间；退款不超过实付 |
| 新鲜度 | 规则 | 最新订单距检查日期不超过 7 天 |

- 报告里问题行只给主键，不带其他列的值；接口只对不受限角色开放（报告不按行列权限裁剪）。
- 规则里的表名、列名先和真实 schema 比对再拼进 SQL。
- 评测：在库的副本上逐个注入 13 类已知缺陷，13 类全部检出；干净库 0 误报（`evals/quality_eval.py`）。

## 后果

- 新增 `semantic.py`、`metrics/shop_ops.yaml`、`quality.py`、`quality_rules/shop_ops.yaml`；接口 `/api/databases/{db}/metrics`、`/api/databases/{db}/quality`；问数事件流新增 `metrics`（本题用到的指标定义）；前端新增"指标目录""数据质量"两页，回答下方可点开口径。
- 问数服务配置版本升到 `e4-v5`，旧缓存自然失效。
- 局限：
  - 字典是看过原 40 题的 evidence 之后写的，原题上的提升有拟合成分；留出题（字典定稿后再写）上同样从 60–65% 提到 100%，但留出题只有 19 道、问法由同一人编写，已经到天花板，区分不出 A 和 B。
  - q25"从来没有下过单"和 q34"都下过单"在标准答案里口径不一致（一个含所有状态、一个只算有效订单），字典没有为"下过单"定义口径，q34 在所有配置下都错。真实场景应该由数据负责人把这类词也写进字典。
  - 只有电商库有字典和质量规则；字典的维护（谁改、怎么评审、版本）没有做流程。

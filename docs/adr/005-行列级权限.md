# ADR 005：行列级权限（语法树改写 + 授权回调兜底）

- 状态：已采纳

## 背景

问数系统给不同角色用：普通员工不该看到成本价、客户姓名，区域经理只该看到自己区域的数据。要求在 SQL 执行前由代码强制，不靠提示词，并且不能削弱现有的三道只读防线。

## 决定 1：用 sqlglot 改写语法树，不用同名 CTE 遮蔽

| 方案 | 做法 | 问题 |
|---|---|---|
| 同名 CTE 遮蔽 | 在 SQL 前加 `WITH orders AS (过滤后的订单)`，未限定的 `orders` 会读到 CTE | `main.orders` 不受 CTE 影响，直接读原表；模型自己写了 WITH 要合并；同名 CTE 嵌套时语义复杂 |
| 视图 + 只读库 | 预先建好每个角色的视图 | 只读连接不能建视图；每个角色一份库，维护成本高 |
| 语法树改写 | 解析后把每一处受限表引用（含别名、子查询、JOIN、UNION、`main.表名`、CTE 内部）替换成"只含可见列、带行过滤"的子查询 | 要逐节点处理；无法解析的 SQL 无法改写 |

- 无法解析的 SQL 在受限角色下直接拒绝（fail closed）；不受限角色仍按原逻辑交给 SQLite（评测口径不变）。
- 显式引用无权访问的列时给出清楚的报错（"当前角色无权访问 products.cost"），而不是 `no such column`，后者会让模型当成写错去乱改。
- 元数据表（`sqlite_master`、`pragma_*`）和其他 schema（`temp.`）在受限角色下拒绝。
- 不受限角色（分析师、没指定角色）SQL 原样执行，不经过改写，避免 sqlglot 重新生成 SQL 带来的语义差异；受限角色的改写用 40 道电商标准答案自检：38 题结果与原样执行一致，2 题（需要敏感列）被拒。

## 决定 2：SQLite 授权回调做列级兜底

SQLite 每读一列都会调用授权回调（`SQLITE_READ`，带表名和列名）。在原有"只放行读操作"的回调外面再包一层：读受限列、读元数据表直接 DENY。即使改写逻辑有漏洞，敏感列也读不出来。行过滤无法在这一层做，只能靠改写。

## 决定 3：展示层、探测工具也按角色过滤

- 表结构（增强 schema、`describe_table`、API 的 schema 接口）：无权访问的列只留列名并标"无权访问"，不给说明、取值、样例；样例只取可见的行。保留列名是为了让模型知道"有这列但不能用"，从而如实告诉用户。
- `search_values` 不搜受限列，只在可见的行里搜；值核对的候选值也只来自可见的行。
- 查询缓存的 key 带角色：否则运营会读到分析师缓存下来的成本价。

## 决定 4：角色从哪来

- 评测：`--role`；问数接口：请求头 `X-Role`（或环境变量 `DATAPILOT_ROLE`）；MCP：启动时的环境变量固定。
- MCP 工具参数里不提供角色：否则模型可以自己传一个更高的角色。
- 项目没有登录系统，`X-Role` 是客户端自报，只用于演示；生产环境必须由网关根据登录身份填写。

## 决定 5：把权限范围告诉模型（不是安全措施，是诚实措施）

评测发现（问题日志 P19）：不告诉模型时，越权仍是 0（代码强制），但需要无权限数据的题只有一半如实告知，行过滤还会让"北京订单数"答成 0。所以在系统提示和回答提示里加上角色说明（`Policy.prompt_note()`），并要求回答说明权限范围。安全靠代码，诚实靠说明，两者分开。

## 后果

- 新增 `src/datapilot/rls.py`；`sql_guard.run_readonly` / `connect_readonly`、`tools`、`schema`、`value_check`、`pipeline`、`service`、`api`、`mcp_server`、前端都增加了可选的角色参数，不传时行为不变。
- 评测判分（`ex.evaluate_one`）在角色下按"该角色能看到的正确结果"判分；问题需要无权限数据时，模型如实拒绝才算对。
- 代码审查发现过两处同名 CTE 绕过行过滤（问题日志 P20）：过滤条件里的表现在一律写成 `main.表名`，受限角色下禁止 CTE 与真实表同名。
- 局限：角色定义写在代码里；行过滤条件由开发者写，未做 SQL 注入式的策略校验；多表行过滤只覆盖了电商库的 users / orders / tickets。

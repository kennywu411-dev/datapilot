# ADR 002：阶段 2 改进实验设计

- 状态：已采纳

## 背景

阶段 1 全量基线（baseline-93aca7）：Haiku 63.0% / Sonnet 71.8% / Opus 86.6%。
Opus 有 241/500 条预测逐字复现标准答案，疑似数据污染（问题日志 P7）。

## 决定 1：主实验模型用 Sonnet，Haiku 验证，Opus 只跑最终配置

| 方案 | 优点 | 缺点 |
|---|---|---|
| 以 Opus 为主 | 准确率最高 | 疑似污染，且已接近上限，改进被掩盖；单价最高 |
| 以 Sonnet 为主 | 污染信号弱，提升空间 28 个百分点，单次全量约 $2.7 | 不是最强模型 |
| 三档都跑每一步 | 信息最全 | 成本约翻倍，Opus 的结论仍不可信 |

Haiku 用来检验"改进是否只对某个模型有效"（第 6 节预判问题），每步也跑，成本可忽略。

## 决定 2：第一步做 Schema 增强，Schema 检索降为消融

BIRD 单库 schema 最大约 2100 token，全量放进上下文没有压力。此时做表检索只会多一种出错方式（漏召回一张表，这题必错）。
所以第一步改为 Schema 增强：把 BIRD 自带的列说明和取值说明（如 `gender: F: female; M: male`）附到 DDL 里，针对"列理解错、取值写错"。
Schema 检索（BM25 + 沿外键补表）仍实现并在 Sonnet 上实测一次，作为消融，用数据回答"这里需要 schema 检索吗"。
不做向量检索：省掉 torch 与 embedding 模型约 1GB 下载；schema 是英文短标识符，BM25 足够做对照。

## 决定 3：值检索放在生成之后，用 SQL 里的字面量去库里核对

先生成 SQL，再用 sqlglot 找出 `列 = '字面量'` / `IN (...)`，到对应列核对是否存在；不存在就用大小写不敏感匹配和 LIKE 找候选真实取值，连同报错一起交给模型改写。
比"从问题里猜关键词再检索"更精确：只在真的写错值时才多花一次调用。

## 决定 4：提示缓存

schema 放进 system 并打 `cache_control`，问题和 evidence 放 user（修复 P4）。改变了提示词结构，所以先单独跑一次"仅移动 schema"的 Sonnet 全量，确认准确率不变，再在此之上叠加改进。

## 实验序列（同一 500 题，Sonnet 全量 + Haiku 全量）

1. E0 基线（已有）
2. E1 缓存版基线：只把 schema 移进 system
3. E2 + Schema 增强
4. E3 + 值核对
5. E4 + 执行反馈纠错（报错 / 空结果，最多 3 次）
6. 消融：E4 配置下把全量 schema 换成 BM25 检索 schema（仅 Sonnet）
7. Agent 版（模型自主调用 list/describe/search_values/run_sql）vs 固定流程最终版：准确率、成本、延迟

## 结果（详见 docs/numbers.md）

- 决定 1 ✓：Sonnet 上各项改进都不显著；Haiku 上 E0 → E4 +4.4pt（p=0.008）。改进对较弱模型有效。
- 决定 2 ✓：Schema 增强无显著提升；Schema 检索显著变差（p=0.013）且成本 ×2.9（缓存失效，P9）。
- 决定 3 ✓：值核对在 500 道标准 SQL 上仅标记 2 题（1323、640，疑似标注问题；最初报 3 题，其中 1001 是别名解析 bug 造成的误报，代码审查后修复），触发少、改错率低。
- 决定 4 ✓：缓存读取占输入 89%，Sonnet 成本 -51%，准确率不变（P4）。
- 固定流程 vs Agent：Sonnet 准确率相同（p=1.0），Agent 成本 +56%、延迟 +55%。最终配置选固定流程 E4。

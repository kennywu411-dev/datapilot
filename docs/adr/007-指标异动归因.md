# ADR 007：指标异动归因（回答"为什么变了"）

- 状态：已采纳

## 背景

问数回答的是"是多少"。经营负责人看到数字之后的下一句通常是"为什么掉了"，这句话现有流程接不住：它会写一条 SQL、给一段回答，要么只把总数复述一遍，要么在回答里自己做减法、挑几个分组说一说，数字对不对、挑得对不对都没有保证。

另外，之前的评测都在 BIRD 基准和一个模拟电商库上做，没有真实业务数据。这一版接入了 UCI Online Retail II（一家英国礼品电商两年的真实交易，约 107 万行），清洗口径和指标定义沿用同一作者的看板项目（[指标定义](https://github.com/kennywu411-dev/ecommerce-dashboard/blob/main/docs/指标定义.md)），用 `scripts/build_retail_ops.py` 构建成 `retail_ops` 库；构建后近 12 个月的 GMV、退货额、订单数与看板的 `findings.json` 逐项相同。

## 决定 1：模型只做两头，中间的分解和算术交给 SQL 和代码

```
问题 ──(模型，结构化输出)──▶ 计划：哪个指标、本期、基期、范围
      ──(代码校验)────────▶ 指标在字典里且可加、日期合法、两段不重叠；不通过就退回普通问数
      ──(SQL + 代码)──────▶ 总变化 → 按维度分解 → 客户 / 商品 / 单据集中度 → 再拆一层 → 剥离
      ──(模型)────────────▶ 把"事实表"写成结论
      ──(代码)────────────▶ 数字核对：对不上就重写一次，再对不上改用模板
```

- 贡献度怎么算是固定的：把指标写成各分组"贡献项"之和。可加指标（GMV、订单数）就是分组的值；差（净销售额）是两个分量之差；比率（退货率 = 退货额 ÷ GMV）取"分组分子 ÷ 整体分母"，各组相加正好等于整体比率，不需要另做"结构效应 / 水平效应"拆分。指标字典里给 derived 指标加了 `formula`（ratio / diff + 两个可加指标），归因据此分解；去重计数（客户数）和没有公式的指标（复购率）不支持，直接告诉用户。
- 每条 SQL 都由代码从指标字典拼出，走和问数相同的 `run_readonly`（只读连接、授权回调、行列级权限改写）；归因请求和问数走同一个接口，限流、排队、缓存（key 带角色）不用另做。
- 不让模型做算术：分组的贡献、预期份额、去掉某个原因后的指标值，都是代码从 SQL 结果算出来的，连同公式和来源 SQL 一起记进事实表。

## 决定 2：按"超额贡献"排序，再扣掉正常波动

只看"谁贡献了最多的变化"会永远指向最大的分组：英国常年占 GMV 的 85%，它"贡献"了 85% 的下降不是原因。

- 超额 = 该分组占总变化的比例 − 它按基期份额本该分到的比例。只占 2% 的德国贡献了 60%，才是异动。
- 真实数据里各分组的份额每个月本来就在摆（新客 / 老客、大单 / 小单尤其明显）。所以再用两个时间段之外的各月数据，算每个分组"份额的月间变化"的 75 分位（四分之三的月份里它的变化不超过这个幅度），份额变化里不超过它 2 倍的部分当作正常波动扣掉。
- 取值很多的维度（客户、商品）只取变化最大的若干个，并且"降得最多的"要和"涨得最多的"配对抵消：大客户每个月都有进有出，超出的部分才算。单据只存在于一个时间段，用"两期同名次的单据互相抵消"当预期。
- 得分不到 20% 就不报原因，如实说"各分组基本同比例变化"。

## 决定 3：下钻最多两层，找到一个原因就把它从数据里去掉再找下一个

- 第一层：6 个普通维度（市场、国家、品类、新老客、客户分层、单据金额分档）+ 客户、商品、单据三个"集中度"维度，一起排序。
- 第二层：只对排第一的原因再拆一次。有一格既占上一层变化的 80% 以上、超额又达到 50%，才把原因细化成"国家 × 品类"这样的交叉；客户 / 商品往下只看是不是集中在某一张单据。
- 剥离：确定一个原因后，在 SQL 里把它排除、重新量剩余变化，对剩下的重复第一层。这样前三个原因是三件不同的事，而不是同一件事的三个切面（一张大额退货单，会同时让"英国""大额""某客户""某商品"都排在前面）。
- 停止条件：已找到的原因合计解释到 80%、剩余变化方向反了、或者没有分组过得分门槛；最多 3 个原因。

## 决定 4：数字核对

回答里的每个数字（先遮掉日期、编号、序数）都要能在已执行的 SQL 结果单元格里、或事实表里找到；按回答里写的小数位数四舍五入后比较。第一次不通过，把对不上的数字告诉模型重写一次；再不通过，改用模板生成结论。界面在回答下面显示"N 个数字全部对上，其中 a 个直接出自 SQL 结果，b 个由代码按公式算出"。

## 决定 5：用固定下钻流程，不用自主 Agent

对照实验（评测方案 `evals/attribution/评测方案.md`，数字和运行 ID 见 numbers.md"v1.6 指标异动归因"）：同一批问题，分别用现有问数流程直接回答、固定下钻流程、拿着 SQL 工具自主下钻的 Agent。结论和依据写在 numbers.md，这里只记决定：

- 采用固定下钻流程。49 例（真实案例 5 + 注入 44）上，第一原因命中固定流程 42.9%、Agent 37–39%，没有显著差别（McNemar p ≥ 0.6）；留出集 22 例上是 31.8% 对 27.3%。Agent 的成本是固定流程的 3.8 倍（Sonnet）到 6.9 倍（Haiku），P50 耗时 1.6–2.8 倍。
- 决定性的差别在数字：固定流程 98 个回答的 1,151 个数字全部能对上 SQL 结果或事实表；Agent 只有 64–72% 直接出自它跑过的 SQL，98 个回答里只有 1 个全部对得上。面向经营负责人的结论，数字来历不明是不能接受的。
- Agent 有一处更好，如实记下：前三命中更高（Sonnet 53.1% 对 46.9%，Haiku 61.2% 对 46.9%，都不显著）。它每次报 2–3 个候选，固定流程解释到 80% 就停、平均只报 0.8 个。如果产品形态是"给分析师列几个值得看的方向"而不是"给负责人一个结论"，Agent 的做法更合适；这是产品取舍，不是谁更准。
- 现有问数流程直接回答（不下钻）只有 10–18%，显著低于两者，不能用来回答"为什么"。
- 固定流程的命中与模型无关（Haiku、Sonnet 都是 21/49），线上归因可以用 Haiku，单次 $0.0007。

## 后果

- 新增 `attribution.py`（流程）、`numcheck.py`（数字核对）、`attr_agent.py`（只在对照实验里用）、`metrics/retail_ops.yaml`、`scripts/build_retail_ops.py`、`evals/attribution/`（评测方案、评测集、注入）、`evals/attribution_eval.py`；问数事件流新增 `attribution`，`answer` 带 `number_check`；前端新增归因视图；retail_ops 新增"海外市场经理"角色。
- 问数服务配置版本升到 `e4-v6`。MCP 工具的名称、参数、返回格式没有改；列表结构时不再把 SQLite 自己的 `sqlite_` 内部表当成业务表列出来（问题日志 P27）。
- 局限：
  - 命中率不高：留出集第一原因命中 31.8%（Wilson 区间 16–53%）。大客户流失、单品断货、复制大额销售单这几类，三种做法都找不到，它们的量级和批发客户平时的进出差不多，只看两个时间段分不出来。
  - dev 上调过三处排序方法（评测方案变更 2），留出集比 dev 低 20 个百分点，有拟合成分。
  - 注入题的入选规则（本维度内偏离同比例变化最多）和默认排序用的是同一类统计量，评测衡量的是"能不能在多个维度和自然波动里挑出来"。
  - "新老客"维度在数据起点附近失真（第一个月所有客户都是新客）：近 12 个月对前 12 个月的 GMV 归因会答成"老客"，而看板人工分析的结论是海外市场和无编号订单。两段都是 12 个月时没有额外的历史月份可以估计正常波动，折扣不起作用。
  - 只比较两个时间段，不看趋势、不做季节性调整；只支持可加指标及其比率 / 差；追问（"那只看德国呢"）没有做，要把范围写进问题重新问。
  - 三种做法各只跑了 1 次。

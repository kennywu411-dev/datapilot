结论：

- 不下钻不行：现有问数流程直接回答"为什么"，第一原因命中 10–18%，显著低于另外两种（p ≤ 0.0075）。它常常只把总数复述一遍，Sonnet 49 个回答里有 17 个没有给出任何具体原因。
- 固定下钻和自主 Agent 的第一原因命中没有显著差别（42.9% 对 37–39%，p ≥ 0.6），和项目在 NL2SQL 上的结论一致；Agent 的成本是固定流程的 3.8 倍（Sonnet $0.0294 对 $0.0077）到 6.9 倍（Haiku），P50 耗时 1.6–2.8 倍。
- 这次有一处不一样：Agent 的前三命中更高（Sonnet 53.1% 对 46.9%，Haiku 61.2% 对 46.9%；留出集上 Haiku 68.2% 对 36.4%，p = 0.065）。都没有达到显著，但方向一致。原因是两者"报几个原因"的策略不同：固定流程解释到 80% 就停，49 例里平均只报 0.8 个原因，其中 15 例一个都不报（没有分组过门槛就如实说没有）；Agent 平均报 2.4–2.7 个。Agent 多报的候选里碰对的更多，代价是它从不说"没有突出原因"。
- 数字能不能追溯，差别是质的：固定流程 98 个回答、1,151 个数字全部能对上（其中 12 个回答第一次核对没过、重写一次后通过，没有用到模板兜底）。Agent 的数字只有 64–72% 直接出自它跑过的 SQL 结果，98 个回答里只有 1 个全部对得上；即使允许"同表两格的一步运算"，仍有 5–8% 的数字找不到来历（98 个回答里有 63 个至少含一个这样的数字）。
- 固定流程的命中与模型无关：分解和排序是代码，Haiku 和 Sonnet 都是 21/49；模型只负责把问题映射成"指标 + 两个时间段"（两个模型都是 49/49）和写结论。所以归因用 Haiku 就够，单次 $0.0007。
- 留出集明显低于 dev（固定流程 31.8% 对 51.9%）。dev 上调过三处方案（评测方案变更 2），有拟合成分；留出集另含 3 种没见过的注入类型。对外引用应以留出集的 31.8% 为准，并说明区间是 16–53%。
- 抽取器的可靠性：固定流程的"读回答文本"口径与"代码排出的原因"口径 98/98 一致；Agent 的文本口径与它 `submit_answer` 里的原因 95/98 一致。

按注入类型看（Sonnet，第一原因命中，dev + 留出）：大额退货单 fixed 4/5、agent 5/5；新客流失 3/3、3/3；客户分层流失 2/2、0/2；无编号订单激增 2/2、1/2；国家 × 品类交叉 2/3、2/3；品类降价 / 促销 2/8、2/8；国家流失 / 激增 1/8、2/8；某国退货潮 1/1、1/1；大客户流失 0/4、0/4；单品断货 0/3、0/3；两个原因 1/3、0/3；复制大额销售单 0/2、0/2。三种做法都找不到的：大客户流失、单品断货、复制大额销售单，这些变化的量级和批发客户平时的进出差不多（问题日志 P23 之后仍然如此），从两个时间段的数据里分不出来。

### 固定流程的方案对照（确定性部分，不调模型、不花钱）

给定标准的指标和时间段，只比较分解、排序、下钻的方案（`attribution_eval.py --ablation`）。第一原因命中 / 前三命中：

| 方案 | dev 27 例 | 留出 22 例 | 相对默认（dev；默认独对 / 它独对） |
|---|---|---|---|
| 默认：超额 − 正常波动 + 两层 + 集中度 + 剥离 | 14/27 = 51.9% · 15/27 | 7/22 = 31.8% · 8/22 | — |
| 按原始贡献排序（不减基期份额） | 1/27 = 3.7% · 1/27 | 2/22 = 9.1% · 2/22 | 13 / 0，p = 0.0002 |
| 不扣正常波动、不做进出对冲（纯超额） | 13/27 · 13/27 | 6/22 · 6/22 | 3 / 2，p = 1.0 |
| 不查客户 / 商品 / 单据集中度 | 11/27 · 11/27 | 6/22 · 6/22 | 3 / 0，p = 0.25 |
| 只用国家 + 品类两个维度 | 12/27 · 13/27 | 5/22 · 6/22 | 3 / 1，p = 0.63 |
| 只拆一层 | 14/27 · 14/27 | 7/22 · 8/22 | 0 / 0 |
| 不剥离（直接取排序前三） | 14/27 · 14/27 | 7/22 · 7/22 | 0 / 0 |
| 波动按 sqrt(间隔月数) 放大 | 12/27 · 13/27 | 7/22 · 8/22 | 2 / 0，p = 0.5 |
| 客户 / 商品不做进出对冲 | 15/27 · 16/27 | 8/22 · 10/22 | 0 / 1，p = 1.0 |

- 唯一显著的是"超额"本身：按原始贡献排序几乎全错（3.7%），因为它永远指向最大的分组（英国、老客、小额单）。这是整个方法里最要紧的一步。
- 其余每一项的差别都在 1–3 例之间，27 例和 22 例都检不出显著。方向上：查集中度（+3 / +1 例）、多维度（+2 / +2）、扣正常波动有帮助；再拆一层、逐个剥离对第一原因命中没有影响，它们改变的是"原因说得多细、前三个原因是不是三件不同的事"，这在只看命中的指标里体现不出来（dev 上只有 1 道交叉题、1 道两个原因的题）。
- 有一项选错了：客户 / 商品的"进出对冲"在 dev 和留出集上都让第一原因命中少 1 例（前三命中少 1–2 例）。冻结方案时依据的是上一轮不完整的对照（当时看是持平），冻结后补跑完整对照才看到。差别不显著，默认方案已经冻结、留出集已经跑过，没有回头改；如实记在这里。
- 两个原因的题（dev 1、留出 2）没有一种方案把两个都找全。
- 确定性部分（22–23 条 SQL，4 线程并行）耗时 P50 0.9–1.1 秒、P95 1.7–2.0 秒；加上两次模型调用，整次归因 P50 约 7 秒。

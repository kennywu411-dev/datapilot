# ROI 测算框架

> 结论：API 成本可以忽略，决定收益的是"人审核一遍要多久"和"系统有多准"。手写一条 SQL 原本不到约 5 分钟的场景，用系统反而更慢。
> 计算脚本：`scripts/roi.py`（改假设后重跑即可）。

## 1. 输入：实测 vs 假设（严格分开）

| 输入 | 数值 | 类型 | 来源 / 依据 |
|---|---|---|---|
| 单次问数 API 花费 | $0.0046 | 实测 | Sonnet 问数服务全流程（含回答生成），`cache-bench-2f535c` 未命中均值 |
| 单次问数延迟 P50 | 3.71 秒 | 实测 | 同上 |
| 准确率（严格） | 72.4% | 实测 | Sonnet E4 三次均值，BIRD 官方 EX 口径 |
| 准确率（外推） | ≈ 90% | 估计 | 50 道失败题人工判定后外推（区间 86–93%），见 `docs/numbers.md` |
| 覆盖率：产出可执行 SQL 的比例 | 99.2% | 实测 | Sonnet E4：496/500 状态正常（3 题生成失控已修复，1 题超时） |
| 超时率 | 0.2% | 实测 | 同上 |
| 分析师手写并验证一条 SQL | 15 分钟 | 假设 | 无实测数据。取"熟悉库结构的分析师写中等复杂度查询"的经验值，敏感性分析覆盖 5–30 分钟 |
| 人审核系统给出的 SQL 与结果 | 2 分钟 | 假设 | 前端已展示 SQL、表格和过程，审核以看 SQL 是否符合口径为主 |
| 系统答错时，人发现并改对 | 10 分钟 | 假设 | 有系统给的 SQL 作起点，比从零写快 |
| 分析师人力成本 | $20 / 小时 | 假设 | 量级参考，可替换为实际值 |
| 月提问量 | 1000 | 假设 | 只影响总量，不影响"划不划算" |

## 2. 公式

```
每题节省（分钟） = 手写时间 − [审核时间 + (1 − 准确率) × 修正时间]
每月净节省       = 每题节省 × 月提问量 / 60 × 时薪 − 单次 API 花费 × 月提问量
盈亏平衡手写时间 = 审核时间 + (1 − 准确率) × 修正时间
```

前提：每个回答都有人审核。在没有人工复核的情况下直接采信系统结果，按严格 EX 每 4 个答案约有 1 个不对，这不是"节省工时"，是在制造错误决策。

## 3. 敏感性分析（月提问 1000 次）

| 手写一题（分钟） | 准确率 | 每题节省（分钟） | 每月节省工时 | 每月净节省 |
|---|---|---|---|---|
| 5 | 严格 EX 72.4% | 0.2 | 4 小时 | $75 |
| 5 | 外推 ≈ 90% | 2.0 | 33 小时 | $659 |
| 15 | 严格 EX 72.4% | 10.2 | 171 小时 | $3,409 |
| 15 | 外推 ≈ 90% | 12.0 | 200 小时 | $3,992 |
| 30 | 严格 EX 72.4% | 25.2 | 421 小时 | $8,409 |
| 30 | 外推 ≈ 90% | 27.0 | 450 小时 | $8,992 |

- 盈亏平衡：严格 EX 下，手写一题 < 4.8 分钟时用系统更慢（2 分钟审核 + 27.6% × 10 分钟修正）。
- API 费用每月约 $4.6，在所有情形里都不到净节省的 7%（最差的 5 分钟、严格 EX 情形：$4.6 vs $75）。所以"净节省 / API 费用"这种倍数（几十到上千倍）没有意义，不作为结论。
- 假设变化的影响排序：手写时间 > 审核时间 > 准确率 > 修正时间 >> API 单价。

## 4. 这套框架怎么用在真实场景

1. 先在真实提问日志上抽样计时，替换"手写时间"和"审核时间"两个假设；
2. 准确率换成在公司自己的库上的评测结果（按 `docs/接入新数据库.md` 的流程接入新库并跑评测），而不是 BIRD 的数字；
3. 把 "覆盖率" 拆细：能答 / 答了但需修正 / 不能答（转人工），分别计时。

## 5. 不能说的

- 不能说"节省了 X 小时"：没有真实用户，节省工时完全来自假设。
- 不能说"ROI 几百倍"：分母是可以忽略的 API 费用，倍数没有信息量。
- 可以说："搭了一个 ROI 测算框架，区分实测和假设，给出盈亏平衡点和敏感性分析；结论是 API 成本可忽略，收益主要取决于审核时间和准确率"。

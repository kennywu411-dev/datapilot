# SOP：做 NL2SQL / Agent 评测时的通用经验

从本项目问题日志（P1–P11）提炼。每条都对应一次真实踩坑，括号里是问题编号。

## 一、评测之前，先证明评测器可信

1. 数据源要逐题对比：同一基准的不同下载源可能不一致（重复题、改过的标准答案），以官方声明的 canonical 版本为准（P1）。
2. 用官方判分函数逐题对照，而不是只比总分：总分对得上，逐题可能对不上（P2）。
3. 做三组自检：标准答案对比自身（得到理论上限）、打乱行顺序（测比较逻辑）、恒返回常数的假 Agent（得到下限）（P2、P3）。
4. 验证测试能失败：故意把被测代码改坏，确认门禁 / 测试会报警；自己和自己比没有区分度（P5）。
5. 注入测试先确认被测对象真的读到了攻击内容，再统计"被带偏 0 次"（阶段 2 注入测试）。

## 二、跑实验时

6. 试跑小样本只用来测单价，不下结论；20 题的置信区间宽到没有意义（试跑 85/90/95% vs 全量 63/72/87%）。
7. 比较配置用配对检验（McNemar），单次运行有约 4–7% 的题会翻转；报告总分用多次运行均值 ± 标准差。
8. 每次付费运行设硬上限：预估会错（思考长度不可预知、缓存失效），上限才是保险（P9）。
9. 改进先看针对的错误类型在目标模型上多不多：值核对和纠错在 Haiku 上显著，在 Sonnet 上不显著（ADR 002）。
10. 怀疑数据污染：强模型逐字复现标准答案、复现标注风格（如 T1 别名）时，它的分数不能当能力（P7）。

## 三、工程上

11. 安全要分层，每层都要有测试证明：SQL 白名单、只读连接、授权回调；只读连接拦不住 ATTACH 和临时表（P6）。
12. 缓存和提示词结构一起设计：可复用的内容放进缓存前缀（P4）；每题不同的前缀会让缓存全部失效（P9）。
13. 截断了就要说：给模型的上下文、给人看的图表，只要截断了，都要明确告知总量（P11）。
14. 缓存 key 的规范化要区分措辞和取值：引号里的值区分大小写，不能一起转小写（P10）。
15. 把生成上限设在正常需要的几倍，而不是几十倍：失控时按上限计费（P8）。
16. SDK 的便捷方法可能吞掉用量信息：解析失败时也要能记账（P8）。

## 四、失败分析

17. 先定判定标准，再判；每个"标准答案错"都要能指出违反了题目或 evidence 的哪一处，并用数据验证（阶段 3）。
18. 抽样要随机分层、固定种子，不挑题，这样比例才能外推（阶段 3）。
19. 模型预分类、人最终判定，并和外部审计结果对照（BIRD 审计论文 52.8% vs 本项目 56%）。

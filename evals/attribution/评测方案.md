# 归因评测方案（先定后跑）

这份文档和 `cases.json`、判分代码在跑任何一次模型之前提交。之后如果改了规则，改动和原因写在文末"变更记录"，不回头改前面的条文。

## 1. 要回答的问题

用户问"某个指标为什么变了"，三种做法谁找得准、谁的数字靠得住、各花多少钱和时间：

| 代号 | 做法 |
|---|---|
| plain | 现有问数流程直接回答：一条 SQL + 一段回答，不下钻 |
| fixed | 固定下钻流程（`src/datapilot/attribution.py`）：模型只做"问题 → 指标和时间段"和"事实表 → 结论"两步，中间的分解、排序、下钻、剥离由 SQL 和代码完成 |
| agent | 模型拿着只读 SQL 工具自主下钻（`src/datapilot/attr_agent.py`），自己决定查什么、查几层、何时停 |

三组看到的表结构、指标口径、可用维度相同；agent 的提示里写了和 fixed 相同的分析思路（看超出基期份额的贡献、查是否集中在少数客户 / 商品 / 单据）。项目之前在 NL2SQL 上的结论是"固定流程和 Agent 一样准、Agent 更贵"，这次不预设结论。

## 2. 评测集（`build_cases.py` 生成，共 49 例）

数据是 UCI Online Retail II 真实交易（`retail_ops` 库）。

### 2.1 真实案例（5 例，全部在 dev）

指标变化来自原始数据本身，标准答案取自看板项目的分析产物，不经过本仓库的归因代码：

| 例 | 问题 | 标准答案的来源 |
|---|---|---|
| real-01 – 03 | 某月退货率为什么比上个月高 | 用看板的 `site/data.json` 按看板发现 3 的方法重算：入选规则是"退货率环比升 ≥ 1.5 个百分点，且当月最大的 ≤ 3 张退货单占当月退货额 ≥ 50%"，24 个月里满足的有 3 个月；答案是这几张退货单 |
| real-04 | 近 12 个月退货率为什么比前 12 个月高 | 看板发现 3：前 10 张退货单占退货额 44.6%，剔除后 3.13% → 1.74%。答出这 10 张里任意一张，或"大额退货单"这一档，算命中 |
| real-05 | 近 12 个月 GMV 增长主要是什么带来的 | 看板发现 1（海外同比 +12.1%，英国 +0.9%）和发现 5（无编号订单 GMV 占比 11.3% → 14.6%）。答海外市场或无编号订单都算命中 |

真实案例少，是因为"原因有据可查"的真实变化本来就少。开发归因流程时看过其中 3 例（real-01、04、05）的输出，所以真实案例只放在 dev，不进留出集。

### 2.2 注入异常（44 例：dev 22、留出 22）

在库的副本里按固定种子制造一个原因已知的变化（`inject.py`）：

| 类型 | 怎么注入 | 主答案 | dev | 留出 |
|---|---|---|---|---|
| country_drop | 删掉某个海外国家当月全部销售单 | 国家 | 3 | 2 |
| country_surge | 把某个海外国家当月的销售单复制 1–2 倍 | 国家 | 2 | 1 |
| category_price_cut | 某品类当月单价打 5–7 折 | 品类 | 3 | 2 |
| category_promo | 某品类当月件数放大到 1.5–3 倍 | 品类 | 2 | 1 |
| large_returns | 插入 1–3 张大额退货单（合计占当月 GMV 的 2.5%–7%） | 这几张单据 | 3 | 2 |
| key_account_churn | 删掉某个大客户当月全部销售单 | 客户 | 2 | 2 |
| new_customer_drop | 删掉当月 80%–100% 的新客销售单 | 新老客 = 新客 | 2 | 1 |
| guest_surge | 把当月无编号销售单复制 1–2 倍 | 新老客 = 无编号 | 1 | 1 |
| product_stockout | 删掉某个畅销商品当月全部销售行 | 商品 | 2 | 1 |
| cross_drop | 只删某国家某品类的销售行 | 国家 × 品类 | 1 | 2 |
| two_causes | 同时删一个国家、给一个品类降价 | 两个原因 | 1 | 2 |
| tier_drop | 删掉某一客户分层当月 80%–100% 的销售单 | 客户分层 | 0 | 2 |
| large_sale_orders | 把当月最大的 1–2 张销售单复制 1–2 份 | 这几张单据 | 0 | 2 |
| country_return_wave | 把某国家当月 50%–100% 的销售单复制成退货单 | 国家 | 0 | 1 |

最后三种只在留出集出现，用来看方案有没有只对见过的类型有效。

- 时间段：当月对比上月，约四分之一对比去年同月；月份随机抽。
- 入选规则：注入之后重新量指标，只保留"注入的效果 ÷ 观测到的总变化"在 0.6–2.0 之间、且总变化不小于基期 1% 的方案。下限保证注入的原因确实是主因；上限排除"注入的变化被反方向的自然波动抵消了大半"的题（那种题问"为什么降了"本身就不成立）。两个原因的题另外要求较小的那个也占总变化的 20% 以上。
- 效果是直接在发票表上算的（`inject.metric_value`），不经过指标字典和归因引擎。
- 问题由模板拼出，指标换用同义词（GMV / 销售额 / 成交额），个别用"上个月"考相对时间。
- 注入用的临时表不落盘，新插入的单据号和原有单据同一格式，库里看不出哪些是注入的。

### 2.3 dev 和留出

- dev（27 例）：用来选排序方法、定阈值、改提示词。
- 留出（22 例）：方案和提示词定稿之后只跑一次，结果如实登记，不再据此调整。

## 3. 标准答案和判定

原因写成一组"维度 = 取值"条件；多于一个条件表示交叉（国家 × 品类）。可用维度：市场、国家、品类、新老客、客户分层、单据金额分档、客户、商品、单据。

哪些说法算对（`cases.json` 的 `gold`）：

1. 主答案：注入时指定的原因（真实案例见 2.1）。
2. 等价说法，按规则由代码在注入时算出：某个维度取值同时满足"影响占比 ≥ 0.8"（被动到的金额变化有 80% 以上落在它里面）和"覆盖率 ≥ 0.8"（它在这个时间段的金额有 80% 以上被动到）。例如注入一张大额退货单时，"这张单据""这个客户""这个商品"通常都满足；"英国"不满足覆盖率，不算对。
3. 比主答案粗的说法不算对（注入的是德国，答"海外"不算）；比主答案细但不满足第 2 条的也不算。
4. 国家已经决定了市场，同时出现时去掉市场再比较。

指标

| 指标 | 定义 |
|---|---|
| 第一原因命中 | 排在第一的原因与任意一个可接受的说法完全相同。两个原因的题，第一原因是两个中的任意一个即算命中 |
| 前三命中 | 前三个原因里有一个命中 |
| 两个原因都找到 | 只对 two_causes：两个注入原因都出现在前三里 |
| 数字一致率（严格，主口径） | 回答里的数字（去掉日期、编号、序数之后）能在这次运行已执行的 SQL 结果单元格里找到的比例；fixed 另外允许对上代码按公式从 SQL 结果算出的事实表。按回答里写的小数位数四舍五入后比较，% 和 0.0313 这样的小数互认 |
| 数字一致率（含一步运算，参考口径） | 额外允许同一张结果表里两个单元格的一步运算（差、比、变化率）。给没有事实表的 plain / agent 一个"心算是否算对"的口径；两两组合会有偶然相等，所以只作参考 |
| 单次成本、耗时 | 该做法自身的模型调用花费和从提问到拿到回答的时间（三组并行跑，耗时会互相影响一点）；抽取器的花费单列，不计入 |

怎么从回答里得到"原因列表"：三组的最终回答文本都交给同一个抽取器（Haiku，结构化输出，提示词见 `attribution_eval.py` 的 `JUDGE_SYSTEM`），整理成按回答里的主次排序的原因列表，再由代码与标准答案比对。主指标用这个"读回答文本"的口径，因为用户看到的就是回答。fixed 和 agent 另有结构化输出（fixed 是代码排出的原因，agent 是 `submit_answer` 的 causes 字段），作为副口径一并报告，也用来检查抽取器：fixed 的文本口径和结构化口径应当基本一致。

显著性：同一模型下两种做法逐例配对，McNemar 精确检验；命中率给 Wilson 95% 区间。49 例只能检出大差距，小差距如实写"不显著"。

## 4. 固定流程自己的对照（不花钱）

fixed 的分解、排序、下钻、剥离是确定性代码。给定标准的指标和时间段，可以不调模型直接比较方案（`attribution_eval.py --ablation`）：

| 方案 | 改了什么 |
|---|---|
| 默认 | 按超额贡献排序（扣正常波动，见变更 2）+ 最多拆两层 + 查客户 / 商品 / 单据集中度 + 逐个剥离 |
| 按原始贡献排序 | 不减去基期份额 |
| 只拆一层 | 不在第一原因之内再拆 |
| 不查集中度 | 只用 6 个普通维度 |
| 不剥离 | 不把找到的原因去掉再找下一个，直接取排序前三 |
| 只用国家 + 品类 | 维度少的情况 |

阈值的初始值在看 dev 之前定下：得分门槛 0.2、细化门槛（占上一层 0.8 且超额 0.5）、解释到 80% 即停、最多 3 个原因。

## 5. 预算

新增模型调用花费上限 10 美元（评测脚本带硬上限，超过即停，可续跑）。先用 3 例试跑量出单例成本，再决定跑哪些模型。

## 变更记录

### 变更 1：评测集加一条入选规则（在跑任何模型、碰留出集之前）

- 起因：第一版评测集（开发仓库的提交 5820d4a）生成后，先用不花钱的确定性消融在 dev 上跑了一遍，默认方案第一原因命中 11/27。逐例看未命中的题，发现很多题的标准答案本身站不住：例如"删掉瑞士 2010 年 5 月的订单"（−£9,745，占净变化 78%），但同一个月瑞典自然少了 £12,300、德国自然少了 £13,500，在"国家"这个维度里，注入的那一格并不是变化最大的，说"瑞士才是原因"没有依据。原规则只要求"注入效果 ÷ 净变化 ≥ 0.6"，净变化小的月份里自然波动互相抵消，这条规则拦不住这种题。
- 改动：加入选规则 3，注入的那一格必须是它自己维度里"偏离同比例变化最多"的一格（偏离 = 该格的变化 − 该格基期份额 × 整体变化；两个原因的题两格都要满足；交叉的题按"国家 × 品类"的组合比较）。`build_cases.py` 的 `dominates`。
- 另外：`large_sale_orders`（复制当月最大的销售单）里，被复制的原单和复制件从数据上分不出来，原单也计入可接受的答案。
- 影响：dev 和留出的注入题按同样的种子重新生成（49 例不变：真实 5、dev 注入 22、留出注入 22）。留出集此前没有跑过任何方案。真实案例不受影响。
- 需要说明的局限：规则 3 用的统计量（偏离同比例变化的大小）和默认排序方法是同一类。它保证的是"标准答案在本维度内成立"；评测衡量的是"能不能在 9 个维度和自然波动里把它挑出来排第一"，不是"超额贡献这个定义本身对不对"。

### 变更 2：排序方法在 dev 上的调整（留出集之前定稿）

最初的方案是"按超额贡献排序"（阈值见第 4 节）。在 dev 上用确定性消融调了三处，全部在碰留出集之前完成，之后冻结：

| 调整 | 起因 | dev 第一原因命中 |
|---|---|---|
| 纯超额（最初方案） | — | 12/27 |
| 扣掉正常波动（份额月间变化的 75 分位 × 2） | 新客 / 老客、大单 / 小单这类分组的份额每个月本来就在摆，摆出来的超额压过了真正的原因 | 14/27 |
| 客户 / 商品的涨跌互相抵消；"维度为空"不当原因 | 偶尔下一次大单的客户、"客户分层为空"（其实就是无编号订单）排到了第一 | 14/27（当时看与上一行持平，保留） |
| 波动按 sqrt(间隔月数) 放大 | 想压住同比对比里"新客占比一年降很多"的假象 | 12/27（变差，不采用，留作对照开关） |

中间还试过用整段历史的标准差、相邻两月之差的均方根来量"正常波动"，都被数据起点的极端值撑大（问题日志 P26），dev 上是 10/27，没有采用。dev 只有 27 例，这些差别都不显著（McNemar p ≥ 0.5）；选择依据是方向和可解释性，不是显著性。留出集上的数字是冻结之后只跑一次的结果。

### 冻结之后的补充（不改方案，只记事实）

冻结并跑完留出集之后，补跑了完整的方案对照（numbers.md"固定流程的方案对照"）。其中"客户 / 商品不做进出对冲"在 dev 上是 15/27、留出集上是 8/22，比默认方案各多中 1 例：上面"持平"的判断来自一轮不完整的对照（当时同时改了"维度为空不当原因"）。差别不显著，默认方案已经冻结，没有回头改。
